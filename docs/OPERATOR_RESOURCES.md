# Operator 资源维护

`operator` 保留普通用户能力，额外维护自己负责的上游账号、创建订阅分组和修改自己分组的名称／描述。管理员继续负责订阅分配、额度调整、公共贡献开关、账号负责人和分组负责人。

## 权限与使用

- 管理员在用户创建／编辑中选择“资源维护者”角色。赋予新权限沿用现有 step-up 验证。
- operator 使用现有“账号管理”“分组管理”入口；管理员仍使用原页面。operator 首次操作需本人完成合规确认。
- operator 新建的账号、分组自动归本人负责。管理员可在账号编辑、分组创建／编辑中指定负责人用户 ID；`0` 清空，恢复仅管理员管理。负责人必须是启用的 operator。
- 账号可以加入本人负责的启用分组，或管理员开启“允许维护者贡献账号”的公共分组。分组与账号的平台必须一致。
- 公共贡献只允许加入／移除自己的账号，不赋予分组管理权，也不赋予其他贡献者账号的管理权。
- 管理员设置的不可见关联由后端保留，包含关联优先级；operator 的关联保存不会覆盖它们。
- 管理权不是调用权。operator 不会因角色或创建分组自动获得订阅；所有新用户继续遵循原默认订阅配置。需要人工发放的实例应保持默认订阅为空。
- 管理员转移负责人后，旧负责人后续请求被拒绝；角色降级后，旧 JWT 的后续 operator 请求也被拒绝。

首版支持 OpenAI／Anthropic／Gemini API Key 账号和 OpenAI OAuth 创建。账号编辑开放名称、并发、优先级及分组关联；凭据替换、启停、删除、导出、批量操作由管理员处理。operator 分组创建可设置日／周／月额度，后续额度修改、订阅分配和续期仍由管理员处理。Simple 模式不开放 operator 订阅分组创建。

可选代理为管理员预先创建并启用的代理，选项只返回 ID 和名称。operator API Key 录入不接受任意上游 URL、`credentials` 扩展对象或请求头覆写；OpenAI OAuth 的代理、回调和会话用途绑定于生成授权链接时的操作者。OAuth 会话只能兑换一次，兑换失败需重新授权。

## 启用与关闭

默认关闭。仅在隔离验证后，在应用进程环境配置：

```sh
OPERATOR_RESOURCES_ENABLED=true
```

重启应用后生效。未设置、设置为 `false` 或拼写错误时，operator 管理接口返回 `404 OPERATOR_DISABLED`。管理员和普通用户的原入口不受该开关影响。关闭开关不会删除资源，也不会撤销已发放订阅。

## 数据及合并边界

迁移 `238_operator_resource_ownership.sql` 只增加：

| 表 | 字段 | 历史数据默认值 |
| --- | --- | --- |
| accounts | manager_user_id | NULL |
| groups | manager_user_id | NULL |
| groups | allow_operator_contribution | false |

未新增表，未重写计费、调度或订阅生命周期。普通管理查询保持原行为；operator 查询带显式范围，计数与分页使用相同条件。operator 更新使用字段白名单和事务，避免陈旧请求覆盖管理员策略或关联失败时部分提交。

管理接口集中在 `internal/server/routes/operator.go` 和 `internal/handler/admin/operator_handler.go`，不会放宽 `/admin` 的认证。前端保留两个原路由，使用小型 wrapper 按角色选择原管理页面或精简组件。Ent 生成文件从 schema 生成；合并上游时先合并 schema，再重新生成，勿手工维护生成结果。迁移正式应用后不得改名或修改内容。

## 验证记录（2026-09-08）

基线为 fork 提交 `aa167a25a7ec3bf27acf1814f64e9157f55197fb`（0.2.3）。验证未连接生产数据库、Redis 或真实上游凭据。

- 前端类型检查、生产构建和 81 项组件／原页面回归测试通过。
- 后端管理员 handler、middleware、routes、repository、DTO、migration 包测试通过；角色、OAuth 和相关业务服务通过定向 race 测试。
- 独立临时 PostgreSQL 16 上通过迁移幂等、资源范围、陈旧快照保护、关联优先级和绑定失败回滚测试，以及原订阅仓储 suite。由于本机没有 Docker，使用临时 Go overlay 将原 testcontainers harness 接到独立 PostgreSQL 和 miniredis，未修改仓库通用测试 harness。
- 本地编译服务通过 33 项 HTTP 检查：管理员创建分组（负责人 0）、operator 创建／编辑、公共贡献、跨资源拒绝、敏感字段拒绝、角色及负责人回收、管理员分配订阅、用户创建 Key 和读取可用模型。
- 用户 Responses 请求通过网关转发到本地 Chat Completions 模拟上游，返回预期内容和 token 数，并从 PostgreSQL 回读匹配的用量记录。
- 未改造的基线二进制在增量迁移后的测试数据库上通过 8 项健康、登录、管理员账号／分组、用户订阅／Key 和模型接口检查。
- 新二进制关闭开关后，operator 管理被拒绝，原管理员和已有 API Key 仍可使用。

这些检查验证了当前 fork 基线的兼容性，不代表历史生产 `0.2.1` 可以直接跨版本升级或回退。Redis 使用 miniredis；真实 Redis、真实 OpenAI OAuth／付费请求和生产发布后验收仍须在部署阶段验证。

## 部署及回退

1. 核对线上准确版本及数据库迁移记录。上游升级与本功能上线分开评估；先备份并验证恢复方式。
2. 先部署到独立测试环境，使用测试用户和专用资源，检查授权、真实 Redis、真实上游 OAuth 和流式调用。
3. 生产部署默认关闭开关，先回归已有用户／管理员及已有 Key，再受控启用。
4. 若只需停止新管理能力，关闭开关并重启。若需换回旧程序，只使用已在相同迁移状态下验证过的版本；不要直接删除新增字段或回滚整库覆盖上线后的正常业务数据。

本次代码推送不包含生产部署授权；未执行生产发布。
